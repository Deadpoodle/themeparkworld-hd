# Sky striping above 2048 px wide

**Symptom.** Above 2048 px wide (tested at 2304x1296 and 2560x1440), the sky in the main-menu fly-by is drawn in every other pixel column, alternating sky colour and black. Water, islands, models and 2D art are correct. The renderer is D3D HAL, windowed, with a 32-bpp back buffer and a 16-bit Z-buffer. The machine is an AMD Radeon RX 9070 XT using the atidx9loader32 driver (testrun\enginedebug.txt).

**Conclusion.** The sky code has no 2048 limit: no per-column table, no span buffer, no step value and no 2048-wide surface. The sky is ordinary D3D geometry. The one thing the sky area has that other areas don't is how its colour gets there. There, the colour you see comes mainly from the D3D viewport **Clear2 colour fill**, in the light blue 0xff44ddff, with translucent sky layers blended on top. Everywhere else, opaque geometry or 2D art overwrites the clear. The striping matches a clear that fills only every other 32-bit pixel when the target is wider than 2048. The most likely cause is the driver's colour-fill path at that width, not engine code (**M**). Engine-side patches that work around it are listed in section 4.

## 1. How the sky is drawn

- **Sky object:** global at 0x008c1828 (`mov ecx, 0x8c1828` at 0x576bf7 and 0x576c73). It is about 0x2f14 bytes. **H**
- **Texture loader, FUN_005852b0** (thiscall, takes a level path). **H**
  - `sky\sky.tga` goes to +0x1fd0. These are the cloud layers.
  - `sky\sky_rgb.tga` goes to +0x1fd4. FUN_00585ce0 samples it into a 16x16 vertex-colour grid at +0xf60 (4 copies), then frees it.
  - `sky\sky_cyl.tga` goes to +0x1fd8. This is the horizon cylinder.
  - Texture flags are OR'd with 0x30200.
- **Mesh builder, FUN_00585720.** Called from engine init FUN_00572780, just before "(tload/rain/sky ok)". **M**
  - Cloud grid: 16x16 vertices at +0x360 (stride 0x30), with an index list at +0x21fc and the count at +0x1f60.
  - Cylinder: 2 x 9 segments x 4 rings = 72 vertices at +0, indexed by 0x120 entries at +0x2c88.
- **Per-frame update, FUN_00585f10.** Scrolls the clouds. Called from FUN_00576a00 when view bit 0x400 is set. **H**
- **Draw, FUN_005863c0.** Called from World_RenderView FUN_00576a00 at 0x576c78 when view bit 0x10 is set. For each cloud layer it does three things:
  1. Starts a primitive with FUN_00565240(2, 4 = triangle list, FVF 0x1c4 = XYZRHW|DIFFUSE|SPECULAR|TEX1, flags, texture).
  2. Transforms the grid with the transform object 0x0087b1d8, vtable +4. FUN_00579330 is the x87 version.
  3. Clips in homogeneous space (outcodes FUN_00561bc0, clipper FUN_00562c90) and submits through FUN_005658c0, FUN_00565590 and D3D DrawIndexedPrimitive (FUN_005680b0).

  The cylinder follows (flags pushed at 0x586aac: `push 0x1d56`). With engine flag 0x2000000 set, the whole sky is drawn a second time, mirrored, for the water reflection. **H** for the flow, **M** for the per-field meanings.
- **Sky render flags.** The cloud-layer flags are computed at 0x58642f–0x58644e: `and cl,8; neg; sbb; and ecx,0xfffffd00; add ecx,0x1556; or ecx,0x400800`. Translated by D3D_ApplyStateFlags FUN_00567620 (**H**):

  | Bit | Effect | Sky value |
  |---|---|---|
  | 0x800 | ZWRITEENABLE | off |
  | 0x100 | ALPHABLENDENABLE | on (low byte 0x56 = blend mode) |
  | 0x400000 | texture address and min filter | wrap, linear |
  | 0x8000 | Z test off | not set, so Z test stays on |

  The cylinder flags 0x1d56 also set ALPHATESTENABLE (0x400). So **every sky layer is translucent and writes no depth.**
- **Sky depth.** Projection mode 1 (FUN_00579690, from header 0x21) writes `z = [0x8bcc3c]` for every vertex. [0x8bcc3c] is 1.0: FUN_005860d0 sets it at 0x5860f9, and it is restored from [0x8bcc1c] = 1.0 (set at 0x582dc1). The sky therefore sits exactly at the far plane. The Z test is LESSEQUAL, against a 16-bit Z-buffer cleared to 1.0. **H**
- **Sun and sky objects, FUN_005860d0.** Billboards drawn through FUN_00565f90 when engine flag 0x400000 is set. **M**
- **Fly-by world setup, FUN_005d8b50** (level `Data\Levels\fantasy`, vtable 0x702a94). **M** that this is the main-menu fly-by.
  - At 0x5d8bef: `mov [0x8bd47c], 0xff44ddff`, the background and fog colour.
  - At 0x5d8bea: `or eax, 0x4000000`.
  - Also sets fog 50..300 and clears flags 0x2000 and 0x10000.

The answer to question 1 is therefore **3D polygons**: translucent cloud layers and a cylinder, depth-tested against the far plane, over the viewport clear. There is no software fill and no 2D background blit.

## 2. What produces the alternating columns

**No engine code is involved.** **H**

- The sky code has no width-dependent logic. In FUN_005863c0 (0x5863c0–0x586e1f) the only global reads are flags and the sky depth. There are no width reads, no 0x800 constants and no shifts.
- The projection uses viewport floats only.
- The D3D viewport is set to the full width (FUN_00572dd0, 0x572e67–0x572ed5: dwWidth = dvClipWidth = [0x8bcbd0]).
- The Z-buffer and back buffer are created at W x H.

**Where the sky-area colour comes from.** **H** for the code.

- Clear2 is the first thing each view does. World_RenderView makes the call at 0x576a51 through `[0x8bd52c]` vtable[0], which goes to thunk 0x573870 and then to D3D_ClearViewport 0x573740.
- At 0x5737aa–0x5737d5: `Clear2(viewport=[this-0x21c], 1, &rect, TARGET|ZBUFFER, (flags & 0x4002000) ? [0x8bd47c] : 0, 1.0, 0)`.
- The rect is (vpX, vpY, vpX + [0x8bcbe8], vpY + [0x8bcbec]), the full width.
- In the fly-by, flag 0x4000000 is set, so the clear colour is 0xff44ddff, the "sky colour".
- The sky layers are blended on top of that clear and never cover it opaquely.

**Why this points at the clear.** **M**

- If the sky polygons were missing in alternate columns, those columns would show the clear's blue, not black. Black means those pixels were never cleared. They keep the 0 from the one-off DDBLT_COLORFILL black fills done at mode setup (0x51b1e2–0x51b232 and 0x563a4f, `push 0x1000400`, fill colour 0).
- Opaque geometry and 2D art overwrite every pixel, which is why they look correct.
- "Exactly width/2" with "colour, black, colour, black" is the signature of a 32-bpp fill done as 64-bit elements over W/2 elements, with the colour put only in the low dword. That fits a driver fill path that applies above 2048 px wide.
- In-park, the clear colour is 0 (black) unless flag 0x2000 or 0x4000000 is set. A zero fill is unaffected by this kind of bug, which would explain why the problem shows only on the blue-cleared front end.

**Three tests that tell the cases apart** (each is a byte patch from the DLL):

1. **Change the clear colour.** Set the fly-by clear colour to magenta: dword at 0x5d8bf5 (the immediate of the `mov` at 0x5d8bef) becomes 0xffff00ff. If the striped colour columns turn magenta, the visible sky is the clear.
2. **Remove the sky geometry.** Skip the sky draw: 0x576c78 `e8 43 f7 00 00` becomes `b8 01 00 00 00` (mov eax,1). If the stripes stay, the sky code is not the cause.
3. **Look at the in-park sky** (camera tilted up) at 2560 wide. If it is clean, the sky code is ruled out again.

If test 1 or 2 does not behave as predicted, the alternative left is a depth or fog problem specific to the far-plane sky (z exactly 1.0 against a cleared D16 buffer of 0xFFFF under LESSEQUAL, plus hardware table fog). The engine-side fix for that is in section 4, option C. **L**

## 3. Other code tied to 2048

None of these limit rendering above 2048:

- **Mouse virtual space 2048x1536.** Globals 0x00faa5c4 and 0x00faa5c0 are written by FUN_006590d0 and read in WndProc FUN_0046b600 and about 30 UI functions. Above 2048, one virtual unit is more than one pixel (1.875 px at 3840), so picking gets coarser, with no corruption. **M**
- **Virtual-space conversions** using 1/2048 (0x703014, 0x6fedf4, 0x6ff15c, 0x74c9c0), 1536.0 (0x6fede0) and 0x600: FUN_005f18d0 and FUN_005f1130 (map-screen mouse), FUN_00476c50, FUN_00485780, FUN_0042a760. These are scaled by width, not clamped. **M**
- **The RESOLUTION 7 width immediate** at 0x44a0ed (already patched).
- **Other `cmp reg, 0x800` hits** are not width-related: event codes (0x4af6ff, 0x498cd9, 0x4a4a6c, after `cmp 0x100`), pool sizes (0x545998, 0x58a6b6, 0x58a6e6), 4096-unit angles (0x55bf95 `and 0xfff`), and detail flags (0x44a5b0). **M**
- **Software renderer (DAT_008bd524 == 4).** Not used with D3D, and not audited here. **L**
- **Z-buffer.** The format enum callback 0x573660 takes the first 16-bit format. 16-bit depth is coarse but does not depend on width. **H**

## 4. Proposed patch (no immediates to change; done in the DLL)

**A. Smallest.** Redirect thunk 0x573873 (`jmp 0x573740`, E9) to a DLL copy of D3D_ClearViewport.

- When [0x7a1968] > 2048, pass Clear2 ceil(W/2048) rects, each at most 2048 wide, in one call. Keep the same flags, colour and z.
- This fixes the problem if the driver's fill path depends on rect width.
- The viewport is [this-0x21c]. The Clear2 slot is vtable +0x50.

**B. If A is not enough** (the fault depends on surface width).

- After the original Clear2, draw one screen-sized pretransformed quad (FVF 0x1c4, z = 1.0, rhw = 1) in the clear colour, inside its own BeginScene/EndScene.
- Render states for the quad: ZENABLE off, ZWRITE off, blend off, alpha test off, fog off, cull none, texture NULL.
- **Get each state first and restore it after.** The engine caches its device state (the shadow flag word used by FUN_00567620) and must not see changes behind its back.
- The device is IDirect3DDevice3 at [this-0x220] in the clear's `this` (object base + 8). **M**
- Use it only when the clear colour is non-zero (the 0x4002000 flags).

**C. Fallback, only if the tests point at the sky rather than the clear.** Move the sky's depth off the far plane:

- 0x582dc1: `mov [eax+0x54], 0x3f800000` becomes 0x3f7ff000 (0.99998).
- 0x5860f9: `mov [0x8bcc3c], 0x3f800000` becomes the same value.
